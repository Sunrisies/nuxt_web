# 后端模拟用户容量验收（2026-10-15）

## 测试定义与结论范围

保留 Nuxt 前端架构，无产品代码变动、无线上部署。本报告直连本地 Rust release + PostgreSQL 17，绕过 Nuxt，只测试公开 GET 接口。525篇样本、回环网络、同机负载发生器。后端二进制与前次验收相同。不能当作线上SLA、实际完整浏览器用户测试、长期稳定性证明或所有业务容量。

模拟活跃读者定义：每人每10秒发送一个后端API请求，用户错峰，以固定频率发起，不根据响应变慢而主动降低发送率，无自动重试。100人=10RPS，300人=30RPS，1000人=100RPS。60%文章详情（分布在525篇），20%分页列表（分布44页，每页12条），10%分类、10%标签。不包含图片、字体、Nuxt SSR、登录、写入、上传、聊天。一人一次实际页面浏览如果产生多个后端API，需要重新换算。

集中点击定义：同一批模拟用户尽快各发一个接口请求；这不是建立同等数量真实浏览器会话，也不是长期保持这么多在途请求。每档3轮。

预设体验门槛（本次工程目标，不是行业统一标准）：
- 持续浏览P95≤500ms、P99≤1000ms、错误率≤0.1%，负载调度延迟P99≤100ms。
- 集中点击P95≤1000ms、P99≤2000ms、零错误。
- 非200、业务code非200、网络/解析错误均计失败；读取完整响应体后计时完成，10秒超时。

## 如何使用这个数字

以通过门槛的实测档位描述能力，不把最高已测档位说成绝对上限。持续读者人数与在途并发不同；1000人每10秒请求一次仅100RPS，并非持续1000并发。三轮突发与60秒稳态均不代替长时间耐久测试。前次596RPS为不同接口配比的饱和测试；本次主要回答明确用户行为下的体验，不能直接对比为性能提升或下降。

当前若目标是1000名读者、每10秒一个读取API，以本地结果判断是否通过；如果目标是多人同时打开完整SSR页面、重写入、较大数据集或目标云主机，需要独立验收。未测得SQL等待/执行计划，不能认定表设计或PostgreSQL是瓶颈。当前无需仅因这些结果重构后端或更换数据库；后续优先补监测和迁移，在目标部署环境复验，并对超过门槛的负载做针对性分析。
